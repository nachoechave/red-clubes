## Reglas de trabajo

- No desarrollar directamente sobre `main` ni sobre `facultad`.
- Crear cada rama desde `develop`.
- Preferir una tarea concreta por rama.
- Asociar la tarea a un Issue cuando sea posible.
- Usar commits descriptivos, por ejemplo:
  - `feat: add group attendance filters`
  - `fix: prevent duplicate enrollment`
  - `test: cover club permission rules`
  - `docs: document reporting flow`
- Abrir Pull Request hacia `develop`.
- Describir qué se hizo, cómo se probó y qué archivos o módulos fueron afectados.
- No atribuir a un integrante código previo al baseline salvo que exista una modificación posterior demostrable.

## Evidencia para la defensa

Para cada integrante se podrá mostrar:

- Issues asignados;
- ramas creadas;
- commits;
- Pull Requests;
- revisiones;
- pruebas agregadas o modificadas;
- documentación técnica asociada.

El objetivo es que la defensa del proyecto pueda explicar no solo el resultado final, sino también el proceso de trabajo colaborativo.
